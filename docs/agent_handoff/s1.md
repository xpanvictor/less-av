# S1 Handoff Spec — VCU Network Bring-Up

> **Read this whole document before writing any code.**
> You are implementing **Stage 1 only**. Do not implement actuator drivers,
> servo/motor control, mode arbitration, or the deadman timer. Those are S2–S3.

---

## 1. Context

**LESS** is a modular autonomy platform. This repo is a bench-rig demonstrator
proving an end-to-end autonomy control path: five nodes, one MQTT broker, all on
a LAN.

The **VCU (ESP32) is the sole authority over actuators.** Every other node
publishes *requests*; the VCU decides. Never dilute this.

S0 is complete and green. It delivered: the Cargo workspace, the `shared`
contract crate (message types, topic constants, limits, validation), Mosquitto
config on ports 1883 + 9001, and the hardware/protocol docs.

**Read `docs/PROTOCOL.md` and `shared/src/lib.rs` before starting.** Everything
you publish must use the types and topic constants defined there. Do not invent
new topics or duplicate type definitions.

## 2. S1 goal

The VCU boots, joins WiFi, connects to the broker, announces itself, and streams
a heartbeat — and the rest of the system can **detect within ~5 seconds when the
VCU dies**. That detection property is the whole point of this stage; everything
downstream depends on it.

### Non-goals (explicitly out of scope)

- No servo or motor code. No LEDC/PWM setup. No `drivers/` directory.
- No subscription handling for `cmd/manual`, `cmd/auto`, `mode/request`, or
  `estop`. S1 is **publish-only**. (Subscribing is S2/S3.)
- No mode state machine, no deadman timer, no arbitration logic.
- No joystick, dashboard, camera, or autonomy work.
- No STM32 work — it remains parked.

## 4. Task 0 — Crate restructure (do this first)

S0 used `#[path = "../config.rs"] mod config;` in `src/bin/main.rs` because a
binary crate root resolves submodules relative to `src/bin/`. That workaround
does not scale to the module tree S1+ needs.

**Convert `vcu` into a lib + bin crate:**

```
vcu/
├── Cargo.toml
├── build.rs                (generated, unchanged)
└── src/
    ├── lib.rs              ← CREATE
    ├── config.rs           (unchanged content, now a lib module)
    ├── net/
    │   ├── mod.rs          ← CREATE
    │   ├── wifi.rs         ← CREATE
    │   └── transport.rs    ← CREATE
    ├── telemetry.rs        ← CREATE
    └── bin/
        └── main.rs         ← MODIFY
```

- `src/lib.rs`: `#![no_std]`, declares `pub mod config; pub mod net; pub mod
  telemetry;`.
- `src/bin/main.rs`: remove the `#[path]` attribute; use `vcu::config`,
  `vcu::net`, etc.
- Confirm `Cargo.toml` produces both a lib target and the bin target. The
  esp-generate default bin path (`src/bin/main.rs`) stays as-is.

Apply the **same restructure to `joystick`** (lib.rs + config.rs module), even
though S1 adds no joystick logic — doing it now keeps both crates symmetrical
and avoids a second migration in S4. The joystick's `lib.rs` need only declare
`pub mod config;`.

**Gate:** both crates still build individually after the restructure, before you
write any network code.

## 5. Task 1 — Transport spike (timeboxed, decide early)

The project uses `esp-rtos` (0.3.0) with `esp-hal` 1.1.1 and `esp-radio`
(0.18.0). Most `rust-mqtt` examples target the older `esp-wifi` + `embassy-net`
combination. Compatibility is **unverified** and is the single largest technical
risk in the build.

**Timebox: ~2 hours of active debugging.** Do not exceed it. If the MQTT client
does not compile and connect within that window, switch to Plan B and move on.
A working demo on Plan B beats a stalled one on Plan A.

### Plan A — native MQTT (preferred)

Integrate a `no_std` async MQTT client (e.g. `rust-mqtt`) over `embassy-net` on
top of `esp-radio`. Must support: CONNECT with client ID, Last Will and
Testament, PUBLISH with retain flag and QoS 0/1.

### Plan B — TCP bridge (fallback, pre-designed)

If Plan A fails, the ESP32 speaks **newline-delimited JSON over a plain TCP
socket** to a bridge process on the Mac, which republishes to MQTT. Downstream
nodes (dashboard, autonomy) see an identical MQTT bus and never know the
difference.

**Wire format** — one JSON object per line, `\n` terminated:

```
{"topic":"less/v1/vcu/state","payload":{...},"retain":false}
```

- Bridge listens on TCP **5555**.
- Bridge republishes each line's `payload` to its `topic` on MQTT, honouring
  `retain`.
- **LWT equivalence:** when the TCP socket closes or times out, the bridge
  publishes `"offline"` retained to `less/v1/vcu/status`. This preserves the S1
  acceptance gate exactly.
- Deliverable if Plan B is used: `infra/bridge.py` (Python, `paho-mqtt`), plus
  `infra/requirements.txt` and README instructions.

**Report which plan you used and why** in your final report. If Plan A worked,
do not build the bridge.

## 6. Task 2 — WiFi connection

Implement in `vcu/src/net/wifi.rs`.

Requirements:

- Credentials come from compile-time environment variables already defined in
  `config.rs`: `WIFI_SSID`, `WIFI_PASSWORD`, `MQTT_BROKER_HOST`. Never hardcode.
- Station mode, DHCP.
- A dedicated always-running connection task that:
  - connects on boot,
  - waits for link-up **and** a DHCP-assigned IPv4 address before signalling
    ready,
  - detects disconnection and **automatically reconnects** without a reboot,
  - applies a backoff of ~2 s between reconnect attempts (do not hot-loop).
- A dedicated always-running network-stack runner task. It must never be
  starved — no long blocking work anywhere on its executor.
- Log the acquired IP address once on connect.

Expose a way for other tasks to know whether the network is up (an
`AtomicBool` or an `embassy_sync` primitive — your choice, but it must be
readable without blocking).

## 7. Task 3 — Broker connection, status, and LWT

Implement in `vcu/src/net/transport.rs`.

Requirements:

- Client ID: `config::MQTT_CLIENT_ID` (`"less-vcu"`).
- Broker host from `MQTT_BROKER_HOST`, port `config::MQTT_BROKER_PORT` (1883),
  or TCP 5555 under Plan B.
- **Last Will and Testament**, registered at connect time:
  - topic `shared::TOPIC_VCU_STATUS`
  - payload: the JSON encoding of `VcuStatus::Offline` (i.e. `"offline"`)
  - retained: **true**, QoS 1
- Immediately after a successful connect, publish `VcuStatus::Online` to the
  same topic, **retained, QoS 1**.
- On connection loss: publish nothing (the broker fires the LWT), retry the
  connection with ~2 s backoff, and re-announce `Online` on success.
- All encoding must go through the `shared` crate's helpers. Do not hand-write
  JSON strings.

## 8. Task 4 — Heartbeat telemetry

Implement in `vcu/src/telemetry.rs`.

- Publish a `VcuState` to `shared::TOPIC_VCU_STATE` at
  `shared::STATE_PUBLISH_HZ` (10 Hz), non-retained, QoS 0.
- Use a drift-free periodic timer (a `Ticker`-style construct), **not** a
  sleep-in-a-loop.
- Field values for S1 (real values arrive in S2/S3):

| Field | S1 value |
|---|---|
| `steer_deg` | `0.0` |
| `throttle` | `0.0` |
| `mode` | `Mode::Estop` |
| `estop` | `true` |
| `link_ms` | `0` |
| `seq` | `0` |
| `uptime_ms` | real milliseconds since boot, monotonic |

> **Boot state is deliberately ESTOP-latched.** The vehicle must require
> explicit arming before it can move. S3 implements the clear path. Do not
> "helpfully" boot into MANUAL.

`uptime_ms` must genuinely increment — it is the acceptance signal that the
heartbeat is live rather than a stuck retained message.

---

## 9. Task 5 — Heartbeat LED

- Toggle `config::PIN_LED_HEARTBEAT` (GPIO2) at 1 Hz from its own task.
- Purpose: an executor-liveness indicator independent of the network. If the LED
  stops while the board is powered, the executor is starved or wedged — this is
  your fastest diagnostic in every later stage.

---

## 10. Structural requirements

- `main.rs` may only: init hardware, init the async runtime, and spawn tasks. No
  business logic, no loops other than what the runtime requires.
- One task per concern: network runner, WiFi connection manager, transport
  (broker) manager, telemetry publisher, heartbeat LED.
- No `unwrap()` on any network operation. Network failure is an expected runtime
  condition, not a bug — handle it and retry.
- No `panic!` paths reachable from normal operation.
- Any task that does non-trivial work between awaits must yield; nothing may
  block the network runner.

## 11. Acceptance tests

Run from repo root. Report actual output for each.

### T1 — Builds

```
cd vcu && cargo build --release
```

**Expect:** exits 0.

### T2 — Flashes, joins WiFi, gets an IP

```
cd vcu && WIFI_SSID='<ssid>' WIFI_PASSWORD='<pw>' MQTT_BROKER_HOST='<mac-lan-ip>' cargo run --release
```

**Expect:** serial log shows WiFi connected and a DHCP IPv4 address on your LAN
subnet. Report the address.

### T3 — Announces online, retained

```
mosquitto_sub -h localhost -t 'less/v1/vcu/status' -v
```

**Expect:** `less/v1/vcu/status offline` (or nothing) before the VCU boots, then
`less/v1/vcu/status online` on connect.

### T4 — Retained status delivered to late subscribers

With the VCU already running:

```
mosquitto_sub -h localhost -t 'less/v1/vcu/status' -C 1
```

**Expect:** prints `online` **immediately** on connect, then exits — proving the
retain flag is set.

### T5 — Heartbeat is live at 10 Hz

```
mosquitto_sub -h localhost -t 'less/v1/vcu/state' -v
```

**Expect:** ~10 messages/second. `uptime_ms` strictly increases. `mode` is
`"ESTOP"` and `estop` is `true`. Payload keys exactly match `docs/PROTOCOL.md`.

### T6 — **LWT fires on power loss (the critical gate)**

With `mosquitto_sub -h localhost -t 'less/v1/vcu/status' -v` running, physically
unplug the ESP32.

**Expect:** within ~5 seconds, `less/v1/vcu/status offline` appears —
published by the **broker**, not the device. Report the measured delay.

> If this fails, S1 is not done. Every downstream stage assumes the system can
> detect a dead VCU. Check the MQTT keep-alive interval (aim for ~5 s, giving
> ~7.5 s worst-case detection) or, under Plan B, the bridge's socket-close
> handling.

### T7 — WiFi reconnect without reboot

With the VCU running, disable the access point (or take the board out of range)
for ~15 s, then restore it.

**Expect:** the VCU reconnects on its own, `status` returns to `online`, and the
heartbeat resumes. `uptime_ms` **continues from where it was** — it must not
reset to zero, which would indicate a reboot rather than a reconnect.

### T8 — Executor liveness

**Expect:** the GPIO2 LED blinks steadily at 1 Hz throughout all tests above,
including during network outages.

## 14. Notes for the developer (not the agent)

**Demo-day WiFi risk.** Credentials are compile-time (`env!`), so changing
networks means a rebuild. Do not discover this at the venue. Set up a fixed
SSID you control now — a Mac Mini hotspot or a small travel router — and build
against it from S1 onward. Venue WiFi with captive portals or client isolation
will also break MQTT between devices regardless of credentials.

**Keep-alive tuning.** T6's detection delay is roughly 1.5× the MQTT keep-alive
interval. A 60 s keep-alive means a ~90 s detection delay, which is useless for
a vehicle. Aim for ~5 s.
