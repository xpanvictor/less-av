# S0 Handoff Spec — Foundation: Workspace, Shared Contract, Broker

> **Read this whole document before writing any code.**
> You are implementing **Stage 0 only**. Do not implement firmware logic, WiFi,
> MQTT clients, or actuator control. Those are S1–S7. Building ahead of the
> stage breaks the acceptance gates and makes handoff untestable.

---

## 1. Project context

**LESS** is a modular autonomy platform. This repo is the demonstrator: a bench
rig (no chassis) that proves an end-to-end autonomy control path.

Five nodes, one broker, all on the same WiFi LAN:

| Node          | Hardware                    | Role                                                                   |
| ------------- | --------------------------- | ---------------------------------------------------------------------- |
| **VCU**       | ESP32                       | Vehicle Control Unit. Owns actuators. Sole authority on mode + safety. |
| **Joystick**  | ESP32 + 2-axis pot + button | Manual drive-by-wire input.                                            |
| **Dashboard** | iPad browser                | Manual control + telemetry over MQTT-WebSocket.                        |
| **Camera**    | ESP32-CAM                   | MJPEG video stream (S6).                                               |
| **Autonomy**  | Mac Mini (Python)           | Publishes autonomous commands (S7).                                    |
| **Broker**    | Mac Mini (Mosquitto)        | MQTT backbone, ports 1883 + 9001.                                      |

The **VCU is the only node that decides what the actuators do.** Every other
node is an _advisor_ publishing requests. This is the core safety property of
the architecture — never dilute it.

### Staging map (context only — you are building S0)

| Stage  | Deliverable                                                                |
| ------ | -------------------------------------------------------------------------- |
| **S0** | **Workspace, `shared` contract crate, broker config, docs** ← you are here |
| S1     | VCU connects to WiFi + broker, publishes status/heartbeat                  |
| S2     | Servo + motor driven by `cmd/manual`                                       |
| S3     | Mode arbitration, deadman timeout, latched ESTOP                           |
| S4     | Joystick node publishes real input                                         |
| S5     | iPad dashboard                                                             |
| S6     | ESP32-CAM MJPEG stream                                                     |
| S7     | Autonomy node closes the loop                                              |

## 2. S0 goal

Establish the compile-time contract and runtime infrastructure that every later
stage depends on, so that no two nodes can disagree about message formats or
topic names.

### Non-goals (explicitly out of scope for S0)

- No WiFi code, no MQTT client code, no `esp-radio`/`esp-wifi` usage.
- No actuator drivers, no servo/motor logic.
- No dashboard HTML/JS beyond a placeholder file.
- No Python autonomy logic beyond a placeholder file.
- No STM32 code. The STM32 is **parked** — reserved for a possible future
  dedicated motor-controller node. Do not scaffold it.
- The `vcu` and `joystick` crates must **compile** but need only contain the
  generated `esp-generate` skeleton plus a `config.rs`. Leave `main.rs`
  essentially as generated.

## 5. The `shared` crate — the contract

This crate is the single source of truth. It has **no hardware dependencies**
and compiles for both `no_std` (firmware) and `std` (host tooling/tests).

### 5.1 Crate configuration

- Attribute: `#![cfg_attr(not(test), no_std)]` so unit tests can use `std`.
  _(This is a common stumbling block — tests will not compile under bare
  `#![no_std]`.)_
- Dependencies: `serde` (default-features off, `derive` feature),
  `serde-json-core`.
- No `defmt` dependency in `shared` — keep it dependency-light. Firmware crates
  can implement `defmt::Format` locally if needed later.

### 5.2 Protocol version

Define a constant `PROTOCOL_VERSION` = `1` and a topic root constant
`TOPIC_ROOT` = `"less/v1"`. Every topic constant must be built from this root so
a version bump is a one-line change.

### 5.3 Topic constants

Expose these as `&'static str` constants. Exact strings:

| Constant name        | Topic string           | Direction                | Retained | QoS |
| -------------------- | ---------------------- | ------------------------ | -------- | --- |
| `TOPIC_CMD_MANUAL`   | `less/v1/cmd/manual`   | joystick/dashboard → VCU | no       | 0   |
| `TOPIC_CMD_AUTO`     | `less/v1/cmd/auto`     | autonomy → VCU           | no       | 0   |
| `TOPIC_MODE_REQUEST` | `less/v1/mode/request` | any → VCU                | no       | 1   |
| `TOPIC_MODE_CURRENT` | `less/v1/mode/current` | VCU → all                | **yes**  | 1   |
| `TOPIC_ESTOP`        | `less/v1/estop`        | any → VCU                | **yes**  | 1   |
| `TOPIC_VCU_STATE`    | `less/v1/vcu/state`    | VCU → all                | no       | 0   |
| `TOPIC_VCU_STATUS`   | `less/v1/vcu/status`   | VCU → all (LWT)          | **yes**  | 1   |

Also expose `TOPIC_ALL` = `"less/v1/#"` for debugging subscriptions.

### 5.4 Message types

All types derive `Serialize`, `Deserialize`, `Clone`, `Copy`, `Debug`,
`PartialEq`. Serialized as **JSON** (interop with JS dashboard and Python
autonomy node is worth more than byte efficiency here).

#### `DriveCommand`

| Field       | Type  | JSON key   | Range / meaning                                       |
| ----------- | ----- | ---------- | ----------------------------------------------------- |
| `steer_deg` | `f32` | `steer`    | Steering angle, degrees. Negative = left.             |
| `throttle`  | `f32` | `throttle` | Normalized. `-1.0` full reverse … `1.0` full forward. |
| `seq`       | `u32` | `seq`      | Monotonic per-publisher counter. Wraps.               |

Use `#[serde(rename = "...")]` to map the short JSON keys.

#### `Mode` (enum)

Variants: `Estop`, `Manual`, `Auto`.
Serialize as **uppercase strings**: `"ESTOP"`, `"MANUAL"`, `"AUTO"`
(via `#[serde(rename_all = "UPPERCASE")]`).

Implement an inherent method `priority(&self) -> u8` returning
`Estop = 3, Manual = 2, Auto = 1`. Higher wins. S3 will rely on this.

#### `ModeRequest`

| Field  | Type   | JSON key |
| ------ | ------ | -------- |
| `mode` | `Mode` | `mode`   |

#### `EstopCommand`

| Field    | Type                   | JSON key | Meaning                                        |
| -------- | ---------------------- | -------- | ---------------------------------------------- |
| `assert` | `bool`                 | `assert` | `true` = engage ESTOP, `false` = request clear |
| `source` | `heapless::String<16>` | `src`    | Who asserted it, for telemetry                 |

_(Add `heapless` as a `shared` dependency for this. If it complicates
serde derive, substitute a fixed `[u8; 16]` — but prefer `heapless::String`.)_

#### `VcuState`

| Field       | Type   | JSON key    | Meaning                          |
| ----------- | ------ | ----------- | -------------------------------- |
| `steer_deg` | `f32`  | `steer`     | Currently applied steering       |
| `throttle`  | `f32`  | `throttle`  | Currently applied throttle       |
| `mode`      | `Mode` | `mode`      | Active mode                      |
| `estop`     | `bool` | `estop`     | Latched ESTOP state              |
| `link_ms`   | `u32`  | `link_ms`   | ms since last _accepted_ command |
| `seq`       | `u32`  | `seq`       | Last accepted command's seq      |
| `uptime_ms` | `u32`  | `uptime_ms` | VCU uptime                       |

#### `VcuStatus` (enum)

Variants `Online`, `Offline`, serialized as `"online"` / `"offline"`
(lowercase). Published retained; `Offline` is the MQTT Last Will payload.

### 5.5 Limits and validation

Expose these as public constants in `shared`:

| Constant            | Value   | Rationale                                 |
| ------------------- | ------- | ----------------------------------------- |
| `STEER_MAX_DEG`     | `35.0`  | Bench servo safe travel, symmetric        |
| `STEER_MIN_DEG`     | `-35.0` |                                           |
| `THROTTLE_MAX`      | `1.0`   |                                           |
| `THROTTLE_MIN`      | `-1.0`  |                                           |
| `CMD_TIMEOUT_MS`    | `300`   | Deadman: no command in 300ms → safe state |
| `STATE_PUBLISH_HZ`  | `10`    | VCU telemetry rate                        |
| `CMD_PUBLISH_HZ`    | `50`    | Joystick/autonomy command rate            |
| `MAX_PAYLOAD_CMD`   | `128`   | JSON buffer sizing                        |
| `MAX_PAYLOAD_STATE` | `256`   |                                           |

> **Note on `STEER_MAX_DEG`:** the real vehicle's Ackermann geometry gives
> asymmetric limits (inner 40°, outer 26.1°). The bench rig has no chassis, so
> S0 uses a symmetric ±35° clamp. When a chassis exists, replace this with the
> asymmetric pair. Record this in `PROTOCOL.md` so it isn't forgotten.

Implement on `DriveCommand`:

- `fn clamped(self) -> Self` — clamps `steer_deg` and `throttle` into range and
  **replaces any NaN or infinity with `0.0`**. NaN handling is mandatory: a NaN
  reaching the servo math produces undefined PWM.
- `fn safe() -> Self` — returns steer `0.0`, throttle `0.0`, seq `0`.
  This is the canonical safe state used by every timeout path.

### 5.6 Serialization helpers

Provide two functions (or inherent methods) per type, or generic over
`Serialize`/`Deserialize`:

- Encode: value → `&[u8]` JSON, writing into a caller-provided buffer,
  returning the used length or an error.
- Decode: `&[u8]` → value, returning `Result`.

Wrap `serde-json-core`'s `to_slice` / `from_slice`. Define a small
`ProtocolError` enum (`Encode`, `Decode`, `TooLarge`) rather than leaking
`serde_json_core` error types across the API.

### 5.7 Unit tests (required)

In `shared/src/lib.rs` under `#[cfg(test)] mod tests`:

1. **Round-trip** each message type: encode → decode → assert equal.
2. **Clamping**: a `DriveCommand` with steer `999.0`, throttle `5.0` clamps to
   `35.0` / `1.0`.
3. **NaN rejection**: steer `f32::NAN` → `0.0` after `clamped()`.
4. **Mode priority ordering**: assert `Estop > Manual > Auto`.
5. **JSON key stability**: encode a known `DriveCommand` and assert the exact
   output string is `{"steer":12.5,"throttle":0.45,"seq":7}`. This test is a
   tripwire — if a future edit renames a field, the dashboard and Python client
   break, and this test catches it at build time.

## 7. Broker configuration

### `infra/mosquitto.conf`

Requirements:

- Listener on **1883** (plain MQTT, for ESP32 nodes).
- Listener on **9001** with `protocol websockets` (for the iPad dashboard).
- `allow_anonymous true` — this is a closed demo LAN; authentication is
  deliberately deferred and must be noted as a known limitation in
  `ARCHITECTURE.md`.
- Bind to `0.0.0.0` so LAN devices can reach it (default is localhost-only on
  some installs — this is a frequent setup failure).
- Persistence off, or to a local `infra/data/` path.
- Log to stdout.

### `infra/run_broker.sh`

A short executable script that starts Mosquitto with this config and prints the
Mac's LAN IP so the developer can paste it into `MQTT_BROKER_HOST`. Use
`ipconfig getifaddr en0` (falling back to `en1`) for the IP. Make it
`chmod +x`.

## 10. Hardware wiring reference (content for `docs/HARDWARE.md`)

### 10.1 Power — read this first

**The MG996R can draw ~2.5 A when stalled.** Powering it from the ESP32's 5V
pin or from the L298N's onboard 5V regulator will brown out the ESP32 and cause
apparently random resets. This is the single most common failure mode in this
build.

Required power topology:

```
  7.4–12V battery / bench supply
        │
        ├──────────────► L298N  +12V  (motor power)
        │
        └──► 5–6V BEC/UBEC (≥3A) ──► MG996R servo V+
                                          │
  USB from Mac ──► ESP32 (logic only)     │
        │                                 │
        └────────── COMMON GROUND ────────┘
                  (ESP32 GND + L298N GND + BEC GND
                   MUST all be tied together)
```

**Common ground is mandatory.** PWM signals are referenced to ground; without a
shared ground the servo and motor driver see garbage.

### 10.2 L298N wiring (one board drives both motors)

| L298N pin   | Connect to                      | Notes                                                                          |
| ----------- | ------------------------------- | ------------------------------------------------------------------------------ |
| `+12V`      | Motor supply positive (7.4–12V) | L298N drops ~2V; use ≥7V for 5V motors                                         |
| `GND`       | Common ground                   | Tie to ESP32 GND                                                               |
| `+5V`       | —                               | Output only if 5V-regulator jumper is ON. Do **not** feed the servo from here. |
| `ENA`       | ESP32 GPIO19                    | PWM, speed motor A. **Remove the ENA jumper.**                                 |
| `IN1`       | ESP32 GPIO21                    | Direction A                                                                    |
| `IN2`       | ESP32 GPIO22                    | Direction A                                                                    |
| `ENB`       | ESP32 GPIO23                    | PWM, speed motor B. **Remove the ENB jumper.**                                 |
| `IN3`       | ESP32 GPIO25                    | Direction B                                                                    |
| `IN4`       | ESP32 GPIO26                    | Direction B                                                                    |
| `OUT1/OUT2` | Motor A terminals               |                                                                                |
| `OUT3/OUT4` | Motor B terminals               |                                                                                |

Direction truth table per channel: `IN1=1, IN2=0` → forward;
`IN1=0, IN2=1` → reverse; `IN1=IN2` → brake/stop. Speed comes from the PWM duty
on `EN`.

> The **jumpers on ENA/ENB must be removed** or the driver runs at fixed full
> speed and ignores your PWM entirely.

### 10.3 MG996R servo

| Servo wire      | Connect to                                        |
| --------------- | ------------------------------------------------- |
| Brown / black   | Common ground                                     |
| Red             | BEC 5–6V output (**not** ESP32, **not** L298N 5V) |
| Orange / yellow | ESP32 GPIO18                                      |

Signal: 50 Hz PWM, 1000 µs = full left, 1500 µs = centre, 2000 µs = full right.

### 10.4 Joystick node (second ESP32)

| Component    | ESP32 pin                                    |
| ------------ | -------------------------------------------- |
| Pot X wiper  | GPIO34                                       |
| Pot Y wiper  | GPIO35                                       |
| Pot ends     | 3V3 and GND                                  |
| ESTOP button | GPIO27 to GND (internal pull-up, active low) |

### 10.5 ESP32 pin constraints (do not violate)

- **GPIO 6–11**: connected to internal flash. Never use.
- **GPIO 34, 35, 36, 39**: input-only. Never drive as outputs.
- **ADC2 pins are unusable while WiFi is active.** Use ADC1 (GPIO 32–39) only.
- **GPIO 0, 2, 12, 15** are strapping pins. GPIO2 is acceptable for the onboard
  LED; avoid GPIO12 entirely (must be low at boot).

### 10.6 S0 bench setup

For S0 nothing needs to be powered or wired — this stage is software only.
Wire the rig during S2. Documenting it now means the pin constants in
`config.rs` are decided before any driver code is written.

## 11. Acceptance tests

All commands run from the repo root. Every one must pass before S0 is
considered green. Report actual output for each.

### T1 — Workspace compiles

```
cargo check --workspace
```

**Expect:** exits 0, no errors. Warnings about unused constants in `config.rs`
are acceptable at this stage.

### T2 — Shared crate tests pass

```
cargo test -p shared
```

**Expect:** all tests pass, including the JSON key-stability test. Report the
test count.

### T3 — Shared crate builds for the firmware target

```
cargo build -p shared --target xtensa-esp32-none-elf
```

**Expect:** exits 0. This proves `shared` is genuinely `no_std`-clean. If it
fails, the `cfg_attr` in §5.1 is wrong or a dependency pulled in `std`.

### T4 — Broker starts

```
./infra/run_broker.sh
```

**Expect:** Mosquitto starts, logs listeners opening on **1883** and **9001**,
and the script prints the Mac's LAN IP.

### T5 — MQTT round trip on 1883

Terminal A:

```
mosquitto_sub -h localhost -t 'less/v1/#' -v
```

Terminal B:

```
mosquitto_pub -h localhost -t less/v1/cmd/manual \
  -m '{"steer":12.5,"throttle":0.45,"seq":7}'
```

**Expect:** Terminal A prints the topic and the exact payload. The payload must
be byte-identical to what the `shared` encoder produces for the same values —
cross-check against the T2 key-stability test.

### T6 — WebSocket listener reachable

```
nc -z localhost 9001 && echo "9001 OPEN"
```

**Expect:** prints `9001 OPEN`. (Full WebSocket handshake is verified in S5.)

### T7 — Retained-message behaviour

```
mosquitto_pub -h localhost -t less/v1/mode/current -m '{"mode":"MANUAL"}' -r
mosquitto_sub -h localhost -t less/v1/mode/current -C 1
```

**Expect:** the subscriber receives the retained payload **immediately** on
connect, then exits. This confirms retained messages work — S3 and S5 depend on
it.
