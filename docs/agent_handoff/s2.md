## 2. S2 goal

Publishing a `DriveCommand` to `less/v1/cmd/manual` moves the servo and spins
the motors. The VCU subscribes, validates, applies, and reflects the applied
values in `vcu/state`.

This stage has **no safety logic yet** — that is S3. Right now, a command
arrives and is applied directly. The value of this stage is proving the full
physical path: MQTT message → VCU → PWM signal → hardware response.

### Non-goals (explicitly out of scope)

- No deadman timer. If commands stop arriving, the last command holds. S3 fixes
  this.
- No mode arbitration. There is only one command source (`cmd/manual`). S3
  introduces the mode state machine.
- No ESTOP logic beyond the boot-ESTOP already in S1. S3 implements clearing
  and latching.
- No joystick node. Commands come from `mosquitto_pub` on your laptop.
- No `cmd/auto` subscription.

## 3. Preconditions

- S1 T1–T8 all green.
- Mosquitto running, bound to LAN (`172.20.10.2:1883`).
- Hardware wired per `docs/HARDWARE.md` §10 **before** flashing S2:
  - MG996R servo on GPIO18, powered from a separate 5–6 V BEC (≥ 3 A).
    **Not from the ESP32 3V3/5V pin. Not from the L298N 5V regulator.**
  - L298N wired per `docs/HARDWARE.md` §10.2: ENA/ENB jumpers removed,
    PWM on GPIO19/23, direction on GPIO21/22/25/26.
  - Common ground: ESP32 GND + L298N GND + BEC GND all tied together.
  - At least one motor connected (OUT1/OUT2 or OUT3/OUT4).
  - Motor supply connected (7.4–12 V) to L298N +12V.
- Verify wiring before powering up: measure continuity, not just visual
  inspection.

> **Power note (repeat from HARDWARE.md):** the MG996R stall current is ~2.5 A.
> Powering it from the ESP32 or L298N onboard regulator will brownout the ESP32,
> producing apparently random resets that look like firmware bugs. Separate BEC
> is mandatory. If the ESP32 resets during any acceptance test, check power
> before debugging code.

## 5. Servo driver (`vcu/src/drivers/servo.rs`)

The MG996R is an analog servo: 50 Hz PWM, pulse width 1000–2000 µs maps to
full left to full right. Use the LEDC peripheral.

### 5.1 Verify LEDC availability

**Do this first, before writing the full driver.** In a throwaway test in
`main.rs` (or a dedicated `#[embassy_executor::task]` that just initialises LEDC
and immediately returns), confirm that `esp_hal::ledc::Ledc::new(...)` compiles
and does not panic at runtime under `esp-rtos` 0.3 / `esp-hal` 1.1.1.

If LEDC is not available or panics, report it and substitute bit-banged PWM via
a hardware timer toggle (document the fallback clearly). Do not silently swap
without reporting.

### 5.2 Driver API

```rust
pub struct Servo<'d> { /* ... */ }

impl<'d> Servo<'d> {
    /// Initialise LEDC channel for 50 Hz on the given pin.
    pub fn new(ledc: &'d mut Ledc, pin: GpioPin<Output<PushPull>>) -> Self;

    /// Set angle. Input is clamped to [STEER_MIN_DEG, STEER_MAX_DEG]
    /// before conversion. Never panics on out-of-range input.
    pub fn set_angle(&mut self, deg: f32);

    /// Return to centre (0°). Called on safe-state.
    pub fn center(&mut self) { self.set_angle(0.0); }
}
```

### 5.3 Angle → pulse width math

```
pulse_us = CENTER_US + (deg / STEER_MAX_DEG) * (MAX_US - CENTER_US)
```

Where `CENTER_US = 1500`, `MAX_US = 2000`, `MIN_US = 1000`, all from
`vcu::config`. This gives a linear mapping: `+35°` → 2000 µs, `0°` → 1500 µs,
`-35°` → 1000 µs.

Clamp `deg` to `[STEER_MIN_DEG, STEER_MAX_DEG]` and sanitise NaN/infinity to
`0.0` **before** the math. These checks are belt-and-suspenders — `DriveCommand`
is already validated by `shared::DriveCommand::clamped()` upstream, but a driver
that assumes clean input is a liability.

### 5.4 LEDC configuration

- Timer: 14-bit resolution at 50 Hz. At 80 MHz APB: prescaler ≈ 98,
  counter max = 16383. Verify with `esp_hal::ledc`.
- Duty for a given pulse width in µs:
  `duty = (pulse_us * (2^resolution - 1)) / period_us`
  where `period_us = 20000` (50 Hz → 20 ms).
- Channel 0, low-speed timer 0.

## 6. Motor driver (`vcu/src/drivers/motor.rs`)

The L298N is a dual H-bridge. Each channel has one PWM enable pin and two
direction pins. Use LEDC channels 1 and 2 (timer 1, 1 kHz, 10-bit resolution)
for the enable pins.

### 6.1 Driver API

```rust
pub struct Motors<'d> { /* channel A + channel B */ }

impl<'d> Motors<'d> {
    pub fn new(
        ledc: &'d mut Ledc,
        // Channel A
        ena: GpioPin<Output<PushPull>>,
        in1: GpioPin<Output<PushPull>>,
        in2: GpioPin<Output<PushPull>>,
        // Channel B
        enb: GpioPin<Output<PushPull>>,
        in3: GpioPin<Output<PushPull>>,
        in4: GpioPin<Output<PushPull>>,
    ) -> Self;

    /// Set both channels to the same speed.
    /// throttle: -1.0 (full reverse) … 1.0 (full forward). 0.0 = stop.
    /// Clamped and NaN-sanitised before application.
    pub fn set_throttle(&mut self, throttle: f32);

    /// Coast to stop (EN pins low, direction pins low).
    pub fn stop(&mut self);
}
```

### 6.2 Direction truth table

| throttle | IN1 | IN2 | Behaviour |
|---|---|---|---|
| > 0 | H | L | Forward |
| < 0 | L | H | Reverse |
| = 0 | L | L | Coast |

Same table for channel B (IN3/IN4). Apply it symmetrically — for S2 the bench
rig drives both channels identically. Differential drive (different speeds per
side) is S3+ work.

### 6.3 PWM duty

`duty = abs(throttle) * (2^resolution - 1)`. Resolution 10-bit → max duty 1023.
Set duty before setting direction pins, so the motor never momentarily runs at
full speed in the wrong direction.

## 7. Subscription and command dispatch
### 7.1 Subscribe on connect

In `vcu/src/net/transport.rs`, after the broker CONNECT succeeds and `Online` is
announced, subscribe to `shared::TOPIC_CMD_MANUAL` with QoS 0.

The S1 agent flagged that adding inbound polling changes the concurrency shape of
`transport_task`. Address it with `embassy_futures::select`:

```rust
loop {
    match select(transport.poll(), TELEMETRY.wait()).await {
        Either::First(incoming) => dispatch_command(incoming),
        Either::Second(state)   => publish_vcu_state(&state),
    }
}
```

Where `transport.poll()` returns the next received MQTT message and
`TELEMETRY.wait()` fires from the telemetry task. This keeps one task owning
the socket while serving both inbound and outbound work.

### 7.2 Command channel

Add a new static in `vcu/src/lib.rs` (or a dedicated `state.rs`):

```rust
pub static RAW_CMD: Signal<CriticalSectionRawMutex, DriveCommand> = Signal::new();
```

`dispatch_command` decodes the payload using `shared`'s decode helper, calls
`DriveCommand::clamped()` on the result, and signals `RAW_CMD`. It must not
panic on a malformed payload — log a warning and continue.

### 7.3 Command application

In `vcu/src/control/actuators.rs`, a task:

```rust
#[embassy_executor::task]
pub async fn actuator_task(mut servo: Servo<'static>, mut motors: Motors<'static>)
```

- Waits on `RAW_CMD.wait().await`.
- Applies `cmd.steer_deg` to the servo and `cmd.throttle` to the motors.
- Stores the applied command in a second static for telemetry to read:

```rust
pub static APPLIED_CMD: Mutex<CriticalSectionRawMutex, DriveCommand> =
    Mutex::new(DriveCommand::safe());
```

Spawn `actuator_task` from `main.rs`.

## 8. Reflect applied values in `vcu/state`

Modify `vcu/src/telemetry.rs` to read `APPLIED_CMD` and populate the telemetry
`VcuState` fields correctly:

| `VcuState` field | S2 value |
|---|---|
| `steer_deg` | last applied `steer_deg` |
| `throttle` | last applied `throttle` |
| `mode` | `Mode::Manual` ← **change from S1's hardcoded `Estop`** |
| `estop` | `false` ← **change from S1's hardcoded `true`** |
| `link_ms` | `0` (real value in S3) |
| `seq` | last applied `seq` |
| `uptime_ms` | real uptime, unchanged |

> **Note:** temporarily setting `mode: Manual` and `estop: false` in the
> telemetry is acceptable for S2 because there is no arbitration yet. S3 will
> wire these to the real mode state machine. Do not build a partial state machine
> here — just publish honest values for what S2 actually does.

## 9. `main.rs` changes

Add to the spawn list only:

```rust
spawner.must_spawn(actuator_task(servo, motors));
```

LEDC and GPIO peripherals are initialised here and passed in. Keep `main.rs`
as init + spawn only.

Peripheral ownership note: `Ledc::new()` takes the peripheral once. Both the
servo driver and the motor driver need LEDC channels. Pass a `&'static mut Ledc`
via `mk_static!`, or initialise both drivers in `main.rs` before spawning and
pass them as owned arguments. Do not share a raw `Ledc` reference between tasks.

## 10. Acceptance tests

Run from repo root. Physical hardware must be wired before these tests. Report
actual output for each.

### T1 — Builds

```bash
cd vcu && cargo build --release
```

**Expect:** exits 0.

### T2 — Servo centres on boot

Flash and observe the servo horn.

**Expect:** within 2 s of power-on, the servo horn moves to or holds centre
(1500 µs). If it twitches to an extreme and holds, the LEDC duty calculation
is wrong. If it does not move at all, LEDC is not initialised or the pin
assignment is wrong.

### T3 — Single command moves servo

```bash
mosquitto_pub -h 172.20.10.2 -t less/v1/cmd/manual \
  -m '{"steer":20.0,"throttle":0.0,"seq":1}'
```

**Expect:** servo horn moves noticeably to the right (positive angle). Hold a
protractor or use the mechanical stop as reference. It does not need to be
precisely 20° — it needs to move in the right direction and hold.

### T4 — Opposite steer

```bash
mosquitto_pub -h 172.20.10.2 -t less/v1/cmd/manual \
  -m '{"steer":-20.0,"throttle":0.0,"seq":2}'
```

**Expect:** servo moves to the left. Confirm it is the mirror of T3.

### T5 — Motor forward

```bash
mosquitto_pub -h 172.20.10.2 -t less/v1/cmd/manual \
  -m '{"steer":0.0,"throttle":0.5,"seq":3}'
```

**Expect:** motor(s) spin forward at roughly half speed. If they spin but in the
wrong direction, swap IN1/IN2 (or IN3/IN4) in the wiring — do not fix it in
software by negating throttle.

### T6 — Motor reverse

```bash
mosquitto_pub -h 172.20.10.2 -t less/v1/cmd/manual \
  -m '{"steer":0.0,"throttle":-0.5,"seq":4}'
```

**Expect:** motor(s) spin in reverse.

### T7 — Stop

```bash
mosquitto_pub -h 172.20.10.2 -t less/v1/cmd/manual \
  -m '{"steer":0.0,"throttle":0.0,"seq":5}'
```

**Expect:** motors stop, servo centres.

### T8 — Combined steer + throttle

```bash
mosquitto_pub -h 172.20.10.2 -t less/v1/cmd/manual \
  -m '{"steer":15.0,"throttle":0.3,"seq":6}'
```

**Expect:** servo at partial right deflection AND motors spinning at ~30% speed
simultaneously.

### T9 — Malformed payload is rejected gracefully

```bash
mosquitto_pub -h 172.20.10.2 -t less/v1/cmd/manual -m 'not_json'
```

**Expect:** VCU logs a warning and continues. Actuator state does not change.
The VCU does not panic or reset. The heartbeat LED continues blinking.

### T10 — Applied values appear in telemetry

While any of T3–T8 is applied, subscribe to `vcu/state`:

```bash
mosquitto_sub -h 172.20.10.2 -t less/v1/vcu/state -v
```

**Expect:** `steer` and `throttle` in the published JSON match what you sent.
`uptime_ms` continues to increment.

### T11 — ESP32 does not reset under load

Run T3 through T8 in sequence with a 1-second pause between each. Watch the
serial log.

**Expect:** no resets, no brownout messages, no `rst:0x...` in the boot log. If
resets occur, stop and check power before any further debugging.
