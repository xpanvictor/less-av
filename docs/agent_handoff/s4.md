## 1. Context

**LESS** bench-rig demonstrator. The joystick node is a second ESP32 (ESP32-CAM
board) that reads a two-axis potentiometer thumbstick and publishes
`DriveCommand` messages to `less/v1/cmd/manual` at 50 Hz.

The VCU receives these commands and drives the actuators. The joystick node has
no knowledge of motors, modes, or ESTOP state — it is a pure input publisher.
ESTOP will be added via the dashboard in S5.

## 2. Hardware

**Board:** ESP32-CAM (AI-Thinker variant). This board uses several GPIO pins
internally for the camera module and SD card slot. The pin constraints below
are hard — violating them will cause boot failures or corrupted camera hardware.

**Joystick module:** two-axis potentiometer thumbstick (standard breakout with
VCC, GND, VRx, VRy). Output range 0–3.3V per axis. Center resting position
is nominally 1.65V (ADC count ~2048 at 12-bit) but will vary per unit —
hence the calibration requirement.

**No ESTOP button.** ESTOP is handled by the dashboard in S5. The joystick
node does not implement any ESTOP path.

### ESP32-CAM pin map

```
Pin     Internal use                    Available for joystick?
──────────────────────────────────────────────────────────────
GPIO0   Camera (PWDN) / boot mode       NO — boot strapping pin
GPIO1   UART TX                         NO — serial monitor
GPIO3   UART RX                         NO — serial monitor
GPIO2   SD card D0                      NO
GPIO4   SD card D1 / onboard flash LED  NO
GPIO12  SD card D2                      NO
GPIO13  SD card D3                      YES if SD not inserted ✓
GPIO14  SD card CLK                     NO
GPIO15  SD card CMD                     NO
GPIO16  PSRAM (if present)              NO
GPIO17  PSRAM (if present)              NO
GPIO32  Camera (XCLK alt)               YES ✓
GPIO33  Onboard red LED (active LOW)    YES — use for heartbeat ✓
GPIO34  Input only, ADC1_CH6            YES ✓ — VRx (X axis / steer)
GPIO35  Input only, ADC1_CH7            YES ✓ — VRy (Y axis / throttle)
GPIO25  Camera (VSYNC)                  NO when camera active
GPIO26  Camera (HREF)                   NO when camera active
GPIO27  Camera (PCLK)                   NO when camera active
```

### Joystick wiring

```
Thumbstick pin    →    ESP32-CAM pin
──────────────────────────────────────
VCC               →    3V3
GND               →    GND
VRx (X / steer)   →    GPIO34
VRy (Y / throttle)→    GPIO35
```


## 4. Calibration (`joystick/src/calibration.rs`)

The thumbstick centre position varies between units. A fixed `ADC_CENTER = 2048`
will produce a persistent steer/throttle offset at rest. Calibration measures
the true centre at boot time.

### 4.1 `CalibrationData`

```rust
pub struct CalibrationData {
    pub center_x: u16,   // measured ADC count at rest, X axis
    pub center_y: u16,   // measured ADC count at rest, Y axis
    pub max_x:    u16,   // ADC_MAX (constant, kept here for symmetry)
    pub max_y:    u16,
    pub min_x:    u16,   // ADC min (always 0 for 12-bit, kept for future)
    pub min_y:    u16,
}

impl CalibrationData {
    pub fn default_uncalibrated() -> Self {
        Self {
            center_x: ADC_CENTER_NOMINAL,
            center_y: ADC_CENTER_NOMINAL,
            max_x: ADC_MAX, max_y: ADC_MAX,
            min_x: 0,       min_y: 0,
        }
    }
}
```

### 4.2 Boot calibration procedure

At boot, before any commands are published, sample both axes for **100
iterations with 5 ms between samples** (500 ms total). Average the readings.
This average becomes `center_x` / `center_y`.

```rust
pub async fn calibrate_at_boot(adc: &mut Adc) -> CalibrationData {
    // Instruction to operator (via serial log only — no display):
    defmt::info!("Calibrating joystick — release all axes for 500ms...");

    let mut sum_x: u32 = 0;
    let mut sum_y: u32 = 0;
    for _ in 0..100 {
        sum_x += read_raw_x(adc) as u32;
        sum_y += read_raw_y(adc) as u32;
        Timer::after(Duration::from_millis(5)).await;
    }
    let cal = CalibrationData {
        center_x: (sum_x / 100) as u16,
        center_y: (sum_y / 100) as u16,
        ..CalibrationData::default_uncalibrated()
    };
    defmt::info!(
        "Calibration done: center_x={} center_y={}", cal.center_x, cal.center_y
    );
    cal
}
```

The operator must not touch the joystick during the first 500 ms after power-on.
Document this in the README boot sequence.

### 4.3 Normalisation

Convert a raw ADC count to a normalised value in `[-1.0, 1.0]`:

```rust
pub fn normalise(raw: u16, cal: &CalibrationData, axis: Axis) -> f32 {
    let (center, max, min) = match axis {
        Axis::X => (cal.center_x, cal.max_x, cal.min_x),
        Axis::Y => (cal.center_y, cal.max_y, cal.min_y),
    };

    // Apply deadzone around centre
    let delta = (raw as i32) - (center as i32);
    if delta.unsigned_abs() as u16 <= DEADZONE_COUNTS {
        return 0.0;
    }

    // Linear map: [min, center) → [-1, 0), (center, max] → (0, 1]
    if raw < center {
        let range = (center - min) as f32;
        let offset = (center - raw) as f32;
        -(offset / range).min(1.0)
    } else {
        let range = (max - center) as f32;
        let offset = (raw - center) as f32;
        (offset / range).min(1.0)
    }
}
```

Result is clamped to `[-1.0, 1.0]` and is `0.0` within the deadzone.

## 5. Input task (`joystick/src/input.rs`)

```rust
/// Shared: input task writes, transport task reads.
pub static JOYSTICK_CMD: Signal<CriticalSectionRawMutex, DriveCommand> = Signal::new();

#[embassy_executor::task]
pub async fn input_task(mut adc: Adc<'static>, cal: CalibrationData)
```

### 5.1 ADC note for ESP32-CAM

ESP32-CAM may or may not have PSRAM depending on the variant. The ADC driver
setup is identical to standard ESP32 — use `esp_hal::adc::{Adc, AdcConfig,
Attenuation}`. Use `Attenuation::Attenuation11dB` for both channels to get the
full 0–3.3V input range.

### 5.2 Task loop

```
Ticker at CMD_PUBLISH_HZ (50 Hz = 20 ms)
├── read raw ADC X (GPIO34)
├── read raw ADC Y (GPIO35)
├── normalise X → steer_norm  ∈ [-1.0, 1.0]
├── normalise Y → throttle_norm ∈ [-1.0, 1.0]
├── scale: steer_deg = steer_norm × STEER_MAX_DEG
│         throttle   = throttle_norm   (already [-1,1])
├── build DriveCommand { steer_deg, throttle, seq }
├── seq increments per publish (wrapping u32)
└── JOYSTICK_CMD.signal(cmd)
```

### 5.3 Axis orientation

Physical thumbstick axes may be inverted relative to expected direction. The
correct mapping is:

- **X axis (GPIO34):** push right → positive `steer_deg` (right turn).
  If inverted, negate `steer_norm` before scaling.
- **Y axis (GPIO35):** push forward (away from you) → positive `throttle`
  (forward). If inverted, negate `throttle_norm`.

Inversion is determined physically after first flash. Add two constants in
`config.rs`:

```rust
pub const INVERT_X: bool = false;  // flip if physical steer is backwards
pub const INVERT_Y: bool = false;  // flip if physical throttle is backwards
```

Apply in `input_task` before scaling:

```rust
let steer_norm    = if INVERT_X { -steer_norm_raw    } else { steer_norm_raw    };
let throttle_norm = if INVERT_Y { -throttle_norm_raw } else { throttle_norm_raw };
```

After first physical test, set these correctly and rebuild. One-line change.

## 6. Network (`joystick/src/net/`)

### 6.1 `wifi.rs`

Identical behaviour to VCU's `wifi.rs`:
- Station mode, DHCP.
- Auto-reconnect with 2 s backoff.
- Signal `WIFI_UP: AtomicBool` when connected.
- Log the acquired IP.

Copy and adapt from `vcu/src/net/wifi.rs`. Change only the log prefix
(`joystick` instead of `vcu`).

### 6.2 `transport.rs`

Simpler than the VCU's transport — **publish only, no subscriptions**.

```rust
#[embassy_executor::task]
pub async fn transport_task()
```

Loop:
1. Wait for `WIFI_UP`.
2. Open TCP socket to broker on port 1883.
3. MQTT CONNECT with:
   - client ID: `MQTT_CLIENT_ID` (`"less-joystick"`)
   - keep-alive: 10 s
   - **No LWT** — joystick disconnecting is not a safety event (the VCU's
     own deadman timer handles link loss independently).
   - clean session: true
4. On connect: log `mqtt: joystick connected`.
5. Publish loop:

```rust
loop {
    let cmd = JOYSTICK_CMD.wait().await;  // blocks until input_task signals

    // Encode using shared helper
    let mut buf = [0u8; shared::MAX_PAYLOAD_CMD];
    match cmd.encode(&mut buf) {
        Ok(n) => {
            client.send_message(
                shared::TOPIC_CMD_MANUAL,
                &buf[..n],
                QoS::AtMostOnce,  // QoS 0 — low latency, loss acceptable
                false,            // not retained
            ).await.ok();
        }
        Err(e) => defmt::warn!("encode error: {:?}", e),
    }
}
```

6. On any error: log, close socket, wait 2 s, reconnect from step 2.

**QoS 0 for commands:** each command is a complete state snapshot (steer +
throttle), not a delta. A lost packet is irrelevant because the next one
arrives 20 ms later. QoS 1 would add ACK round-trips that increase latency
and add little value here.

## 7. Heartbeat LED (`joystick/src/input.rs` or a separate file)

GPIO33 is the onboard red LED on ESP32-CAM, **active LOW** (set LOW to turn on,
HIGH to turn off). Add a heartbeat task:

```rust
#[embassy_executor::task]
pub async fn heartbeat_task(mut led: Output<'static>)
```

Blink at 1 Hz during normal operation. Blink at 4 Hz (fast) while WiFi is
connecting or MQTT is disconnected. This gives a visual status without a
serial monitor.

```rust
loop {
    let fast = !WIFI_UP.load(Ordering::Relaxed);
    let interval = if fast { 125 } else { 500 };
    led.set_low();   // LED on (active LOW)
    Timer::after(Duration::from_millis(interval)).await;
    led.set_high();  // LED off
    Timer::after(Duration::from_millis(interval)).await;
}
```

## 8. `main.rs`

```rust
#[esp_rtos::main]
async fn main(spawner: Spawner) -> ! {
    let config = esp_hal::Config::default().with_cpu_clock(CpuClock::max());
    let peripherals = esp_hal::init(config);

    // Runtime init (same pattern as VCU)
    let timg0 = TimerGroup::new(peripherals.TIMG0);
    let sw_interrupt = SoftwareInterruptControl::new(peripherals.SW_INTERRUPT);
    esp_rtos::start(timg0.timer0, sw_interrupt.software_interrupt0);

    // ADC setup
    let mut adc_config = AdcConfig::new();
    let axis_x = adc_config.enable_pin(peripherals.GPIO34, Attenuation::Attenuation11dB);
    let axis_y = adc_config.enable_pin(peripherals.GPIO35, Attenuation::Attenuation11dB);
    let adc    = Adc::new(peripherals.ADC1, adc_config);

    // Calibrate at boot (500 ms, joystick must be released)
    let cal = calibration::calibrate_at_boot(&mut adc, axis_x, axis_y).await;

    // LED
    let led = Output::new(peripherals.GPIO33, Level::High, OutputConfig::default());
    // GPIO33 active LOW — initialise HIGH = LED off

    // Spawn
    spawner.must_spawn(input::input_task(adc, axis_x, axis_y, cal));
    spawner.must_spawn(net::wifi::wifi_task());
    spawner.must_spawn(net::transport::transport_task());
    spawner.must_spawn(input::heartbeat_task(led));

    loop { core::future::pending::<()>().await; }
}
```

Note: `main` does not return — use `core::future::pending()` to park after
spawning, rather than a `Timer::after` loop. Keeps main strictly init + spawn.

## 10. Acceptance tests

Flash to the ESP32-CAM. VCU must be running and armed (ESTOP cleared, mode
MANUAL) before running T3 onwards. Run `mosquitto_sub -h 172.20.10.2 -t
'less/v1/#' -v` in a terminal throughout.

### T1 — Builds

```bash
cd joystick && cargo build --release
```

Expect: exits 0.

### T2 — Calibration runs at boot

Flash and observe serial log immediately after power-on. **Do not touch the
joystick.**

Expect:
```
[INFO] Calibrating joystick — release all axes for 500ms...
[INFO] Calibration done: center_x=XXXX center_y=XXXX
[INFO] wifi: connecting...
[INFO] wifi: DHCP address 172.20.10.X/28
[INFO] mqtt: joystick connected
```

`center_x` and `center_y` should be near 2048. Values between 1800–2300 are
normal. Values near 0 or 4095 indicate a wiring problem (axis pin floating or
shorted to rail).

### T3 — Joystick at rest publishes zero command

With joystick released (centred), watch `less/v1/cmd/manual`:

Expect: `{"steer":0.0,"throttle":0.0,"seq":N}` at ~50 Hz. `steer` and
`throttle` must be `0.0` (deadzone active). If they drift by ±0.1 or more,
the deadzone constant is too small — increase `DEADZONE_COUNTS` in `config.rs`.

### T4 — X axis steers

Push the thumbstick fully right. Watch `cmd/manual`.

Expect: `steer` approaches `35.0` (STEER_MAX_DEG). Push fully left — `steer`
approaches `-35.0`. Release — returns to `0.0`.

If the direction is inverted (right push gives negative steer), set
`INVERT_X = true` in `config.rs` and rebuild.

### T5 — Y axis throttles

Push thumbstick fully forward. Watch `cmd/manual`.

Expect: `throttle` approaches `1.0`. Pull fully back — `throttle` approaches
`-1.0`. Release — returns to `0.0`.

If inverted, set `INVERT_Y = true` and rebuild.

### T6 — Car responds to joystick

With VCU armed and motors connected:

Push joystick forward.

Expect: all four wheels spin forward. Car moves. Push right — car arcs right
(front right wheel slower). Release — deadman fires within 300 ms, motors stop.

### T7 — Deadman fires on joystick release

Push forward for 2 s, then release joystick (steer=0, throttle=0 from deadzone).

Expect: VCU serial log shows `[WARN] arbiter: command link silent` within
~450 ms of releasing. Motors stop. Note: the joystick is still publishing
`{"steer":0.0,"throttle":0.0}` — this IS a valid command that resets
`LAST_CMD_MS`. So the deadman should NOT fire while the joystick is held at
centre — only if the joystick node loses WiFi or power.

> **Clarification:** the deadman fires when no MQTT message arrives, not when
> throttle is zero. A zero-throttle command still resets the timer. Test true
> deadman by powering off the joystick ESP32-CAM while motors are running.
> Motors should stop within 450 ms.

### T8 — True deadman: power off joystick

With motors running from joystick input, physically unplug the ESP32-CAM.

Expect: VCU serial shows `[WARN] arbiter: command link silent` within 450 ms.
Motors stop. VCU remains in MANUAL mode (deadman does not change mode).

### T9 — Joystick reconnects cleanly

After T8, plug the ESP32-CAM back in. Wait for it to reconnect (~10 s for
boot + calibration + WiFi + MQTT).

Expect: joystick resumes publishing. VCU responds to input again without any
manual re-arm. (The VCU stayed in MANUAL mode through the deadman event.)

### T10 — Heartbeat LED behaviour

Observe the onboard red LED:

- During boot (WiFi connecting): fast blink ~4 Hz.
- After MQTT connected: slow blink ~1 Hz.

Expect both states to be visually distinct.
